# Al Fanar Travel — Arabic RTL booking landing pages

Four conversion-focused booking pages that turn a visitor into a complete, structured WhatsApp booking request with a unique lead ID and campaign attribution.

| Route | Purpose | Google Ads use | Form → WhatsApp CTA |
|---|---|---|---|
| `/hotels` | **Primary page** for hotel search traffic | Final URL for حجز فندق / حجوزات الفنادق / حجز فنادق ad groups | اطلب خيارات الفنادق عبر واتساب |
| `/flights` | General & frequent-flyer ticket requests | Flight ad groups | اطلب خيارات تذاكر الطيران |
| `/flights/honeymoon` | Honeymoon planning | Honeymoon ad groups | خطّط لرحلة شهر العسل |
| `/flights/umrah` | Umrah arrangements | Umrah ad groups | استفسر عن خيارات العمرة |
| `/` | Category selector (do **not** use as an ad final URL) | — | — |
| `/privacy`, `/terms` | Legal placeholders (noindex until approved) | — | — |

Navigation: **الفنادق** first, then **تذاكر الطيران** with sub-items **شهر العسل** and **العمرة**, then تواصل معنا.

## Brand tokens

`site.css :root` — `--blue #28387F` (header/nav, hero and section backgrounds, selected service tab, footer), `--yellow #FFD12B` (all primary/WhatsApp CTAs, active nav underline, headline emphasis), `--white`, plus dark-navy `--blue-dark/--blue-ink` for overlays and shadows. Text on yellow is always blue (≈7.7:1 contrast). Cairo 800 headings / 700 subheads & buttons / 400–500 body; Poppins for Latin.

## Stack and why

Plain HTML/CSS/vanilla JS generated by a zero-dependency Node script. No framework runtime ships to the browser, so pages are ~45 KB of HTML + 1 CSS + 2 small JS files — good for Core Web Vitals on mobile Google Ads traffic. Every page is static and can be hosted on Vercel, Netlify, Cloudflare Pages or any CDN. If the team later standardises on Next.js, the `src/` modules (copy, field definitions) port directly into components.

```
site.config.json        ← single source of truth for business details (WhatsApp number, logo, licences, GTM…)
build.mjs               ← node build.mjs → dist/ (production)   |  node build.mjs --preview → preview/ (relative links)
src/pages.mjs           ← all page copy, form field definitions, FAQs
src/ui.mjs              ← layout, header/nav, footer, form renderer, image slots, sections
src/icons.mjs           ← inline SVG icons
public/assets/css/site.css
public/assets/js/app.js   ← nav, consent mode v2, UTM/GCLID capture, dataLayer, sticky CTA
public/assets/js/forms.js ← validation, progressive disclosure, lead ID, WhatsApp message, lead recording
public/assets/img/        ← optimised photos + brand/ logo & favicons (see docs/IMAGE_MAP.md)
images-src/               ← original client photos (input for tools/images.mjs)
docs/design-references/   ← the 4 client page designs (reference only, not deployed)
api/lead.js             ← Vercel function: validates and forwards leads to CRM/Sheet webhook (secrets server-side)
tools/images.mjs        ← makes AVIF/WebP/JPEG 800/1600 variants from approved originals
vercel.json             ← build, clean URLs, cache + security headers
docs/                   ← tracking plan, image map, QA checklist, launch blockers, Ads notes
```

## Run

```bash
node build.mjs            # production build → dist/
npx serve dist            # or any static server
node build.mjs --preview  # relative-link build for sharing a preview
```

The build prints every item still pending approval. While `showPlaceholders` is `true`, placeholders are shown in yellow, a pre-launch banner appears, pages are `noindex` and `robots.txt` disallows crawling. Setting `showPlaceholders: false` **refuses to build** until the required items are filled in.

## Deploy (Vercel)

1. Import the repo. Build command and output dir come from `vercel.json`.
2. Set env vars for `api/lead.js`: `LEAD_WEBHOOK_URL`, `LEAD_WEBHOOK_SECRET`, `ALLOWED_ORIGINS`.
3. Fill `site.config.json`, add approved images, set `showPlaceholders: false`, rebuild.
4. Run `docs/QA_CHECKLIST.md` on the production URL before switching Ads final URLs.

## How a lead flows

1. Visitor fills the service form (required fields first; optional preferences in a collapsible section; conditional fields appear only when relevant).
2. Client-side validation in Arabic (dates not in the past, checkout after check-in, return on/after departure, infants ≤ adults, budget or «مرنة», at least one Umrah service…).
3. A lead ID is generated: `AF-<H|F|HM|U>-<YYMMDD>-<5 chars>` (e.g. `AF-H-261112-7KQ2M`).
4. The lead record (fields, message, UTM first/last touch, GCLID/GBRAID/WBRAID **only with ad consent**, consent state) is sent with `sendBeacon` to `/api/lead`, which forwards it to the CRM/Sheet.
5. A complete Arabic message (service, lead ID, route/destination, dates with weekday, nights, guests, rooms, budget in KWD, preferences) is URL-encoded into `https://wa.me/<number>?text=…`.
6. WhatsApp opens automatically inside the submit gesture; a success panel shows the lead ID, the message, an **Open WhatsApp** button, **Copy message** fallback and **Edit request**. The copy explicitly tells the customer to press **Send**.
7. Status at this point is `whatsapp_prefilled` — not sent, not qualified. See `docs/TRACKING_PLAN.md`.

Business details still needed are listed in `docs/LAUNCH_BLOCKERS.md`.
